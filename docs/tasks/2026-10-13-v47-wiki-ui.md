## 1. 배경

- 검색 화면(`wiki.html`)은 검색어를 넣어야 결과가 나오고(최대 30건), 토픽은 하나만 고를 수 있었다. 3,162건을 훑거나 여러 조건으로 거를 방법이 없었다.
- 대표님 요청(10-13): ① 처음 열면 전체 목록 ② 건수 선택 제거 ③ 토픽 다중 선택 ④ 정렬 목록 유지 ⑤ 필터 추가 ⑥ 목록 칼럼 정렬. 디자인 검토 제안 중 결정: 의미 검색 관련 결과 = 상위 200건 · 비슷한 영상 · 새로 들어온 것 · **엑셀** 내려받기 · 노트 전체 보기 · 밝은 테마만.
- 회사 디자인 시스템(iRichGreen Design System) 웹 계층 **DS 1.1.23(FD 기준판)** 을 따른다.

## 2. 설계 결정 (바꾸지 말 것)

| 항목 | 결정 |
|---|---|
| 목록 | 화면이 `/api/wiki-search?all=1` 을 한 번 받아(약 3.5MB → gzip 0.73MB, ETag 로 304) 필터·정렬·건수를 브라우저에서 계산 |
| 검색 | `?scores=1&q=` 가 **모든 노트의 점수**를 준다. 의미 검색이면 화면이 점수 상위 200건을 「관련 결과」로 보고 그 안에서 거른다. 임베딩 실패면 글자 일치(0점 제외) |
| 비슷한 영상 | `?similar=<id>` — 저장된 벡터끼리 코사인, 상위 5. **Gemini 호출 없음** |
| 노트 보기 | 새 경로 `GET /api/wiki-note?id=` — **경로를 받지 않고 id 로만** 인덱스에서 찾는다. `readNote` 의 Vault 밖 차단은 그대로. 집 안 서버 라우트에 이것 하나가 늘어난다(읽기 전용) |
| 기존 호환 | `?q=&limit=` 응답(`results`) 그대로 — AI 답변 503 대체 경로와 MCP(`wiki_mcp.js`, 라이브러리 직접 호출)가 쓴다 |
| 인덱스 | `build_search_index.py` 가 화면 필터용 `kind`·`subscriber_count`·`summary_src`·`link_url`·`category`·`importance`·`keywords` 를 더 담는다. 메타는 매 빌드 프론트매터에서 다시 읽고 **임베딩 hash 와 무관** — 사전 검증에서 실 Vault 로 재사용 3,162 · 신규 임베딩 0 |
| 엑셀 | 브라우저가 .xlsx 를 직접 만든다(외부 라이브러리·네트워크 없음). 파일명 `ai-llm-wiki-YYYYMMDD.xlsx`, 시트 「목록」(머리줄 고정·자동 필터·링크)·「조건」(검색어·필터) |
| 새로 들어온 것 | 그 브라우저 localStorage(`wiki.seen`·`wiki.new`)에만. 서버·장부에 쓰지 않는다 |
| 디자인 | DS 1.1.23 토큰을 `wiki.html` 머리 CSS 변수로만(밝은 테마만). FilterChip(목록 거르기)·SegmentedControl(보기·토픽 조건)·표 30px 줄·카드 그림자 없음·최소 12px·고정폭 숫자·1만 이상 「만」·빈 값 `-` |
| 테스트용 환경변수 | `WIKI_SEARCH_DIR`·`WIKI_VAULT` 는 `scripts/test_wiki_search.js` 가 임시 폴더를 가리킬 때만 쓴다. `.env` 에 넣지 않는다 |
